## Problem Statement

Archos Labs runs two tracks: consulting (revenue) and free AI-powered tools (lead gen — currently only the Executive AI Diagnostic at `/tools/ai-readiness`). AI-generated content now carries provenance signals of two structurally different kinds: (1) deterministic metadata fields — C2PA content-credential manifests, EXIF/XMP tags, incidental invisible-Unicode artifacts — which can be read and deleted mechanically; and (2) cryptographic/statistical watermarks embedded in the token distribution itself (Claude's Aug 2026 watermark, Google's SynthID-Text), which have no public detector and cannot be reliably found or removed by any third-party tool, including this one. This regulatory backdrop (EU AI Act Article 50, enforced since Aug 2, 2026; CA SB 942; China GB 45438) is why the space is topical right now — it is not a claim that this tool addresses statistical watermarks. Archos Labs' existing audience — compliance-conscious consultants, execs, and data/AI leaders in regulated industries — is the group that would want to strip *metadata-level* provenance signals from a client deliverable before sending it, without exposing the file's content to a third-party server. A second free tool, modeled functionally on `github.com/guillaumemeyer/watermarks-remover` and stylistically on `watermark.sabrina.dev` (scoped down from both — see Premises), extends the same lead-gen pattern that shipped the Diagnostic. Conversion mechanism: same as the Diagnostic's brand-halo role — a persistent, non-blocking CTA into the consulting track, not a registration gate (see Premise 6 for why anonymous was chosen over gated).

## Demand Evidence

No first-party evidence — no named Archos Labs client has hit this yet. Borrowed, category-level evidence only: sabrina.dev has real traction (the "GitHub tool targets Claude watermarks" story spiked watermarks-remover to ~4,100–17k GitHub stars in 48 hours per Implicator.ai, right after Anthropic's Aug 14, 2026 watermark FAQ); "AI watermark remover" search interest was up 60% week-on-week (Google Trends, via AOL coverage). Flagged explicitly as a risk: this is evidence the *category* gets traffic, not evidence Archos Labs' own audience converts — which is also why v1 scope is deliberately narrower than the full reference-tool feature set (see Target User & Narrowest Wedge).

## Status Quo

Two positions surfaced in discussion: (1) most people don't know invisible watermarks or provenance metadata exist in their content at all — the status quo is unawareness, not effort; (2) scattered free/unbranded tools already exist (sabrina.dev, `guillaumemeyer/watermarks-remover`, `wiltodelta/remove-ai-watermarks`) but carry no trust signal and no guarantee they don't log uploaded content server-side.

## Target User & Narrowest Wedge

Target: the same ICP as the Executive AI Diagnostic — a compliance-conscious consultant, exec, or lawyer stripping AI provenance metadata from a client deliverable before sending it (worried about undisclosed-AI-use optics, or leaking which AI tool/version drafted it), not a broad consumer audience.

**v1 wedge, narrowed from the original full-parity scope given zero first-party demand evidence:**
- **Text:** strip a fixed, named set of invisible Unicode code points — zero-width space (U+200B), zero-width non-joiner (U+200C), zero-width joiner (U+200D), word joiner (U+2060), zero-width no-break space / BOM (U+FEFF), narrow no-break space (U+202F), em space (U+2003), thin space (U+2009), bidi control characters (U+202A–U+202E, U+2066–U+2069), variation selectors (U+FE00–U+FE0F), and the Unicode tag block (U+E0000–U+E007F). This set is adopted from this project's own landscape research (Rumi's April 2025 report on OpenAI's o3/o4-mini leaving U+202F/U+200B/U+2003) plus the standard invisible/bidi ranges documented by existing open-source strippers.
- **Images, JPEG + PNG only:** EXIF, XMP, and C2PA (JUMBF box) removal via a **hand-rolled marker/chunk parser**, not a third-party library — see Approach C for why. WebP, HEIC, SVG explicitly **out of scope for v1** (different container mechanics per format — see Open Questions).

Flow: paste text or drop a JPEG/PNG → see exactly which signals were found → strip → copy/download. No auth, no account (decided — see Premise 6), matching sabrina.dev's "no setup, no signup" and the existing CLAUDE.md mandate for frictionless, instant tools.

**Explicitly deferred to a phase 2 decision, not committed here:** PDF, DOCX/XLSX/PPTX, and additional image formats (WebP/HEIC/SVG). Each needs its own spike before scoping in — see Open Questions.

## Constraints

- Next.js 16 App Router, TypeScript, single Render web service (per `wiki/entities/deployment-architecture.md`) — no second runtime/service.
- No prices or dollar amounts on the site (CLAUDE.md).
- Never log tool content server-side — extends the existing "never log diagnostic answers or report content" precedent. Made structurally true here: there is no server-side content path at all in v1.
- Rate limit 100 req/IP/hour on any API endpoint added (CLAUDE.md) — moot for v1 since v1 has no API route; kept as a standing constraint if a server endpoint is ever added later.
- **No feature may attempt to defeat a cryptographic or statistical AI-content watermark** (Claude's, SynthID-Text, or any vendor's), including via paraphrase/rewrite. This is a hard scope boundary, not a business-risk tradeoff the way the metadata-stripping brand-risk is — see Premise 5.

## Premises

1. The real-world product category (sabrina.dev, both GitHub repos, BypassGPT/HIX Bypass/Undetectable AI) is dominated by AI-detection/plagiarism-evasion use — the vendors' own marketing names Turnitin/GPTZero/Originality.ai as targets — not privacy hygiene. **Confirmed** by 5-angle landscape research; user acknowledged and accepted the tradeoff.
2. Building a metadata-stripping tool in this space puts Archos Labs in adjacent territory to plagiarism-evasion products, in tension with the trust-first governance brand for regulated-industry clients. **Confirmed** as a real risk; user chose to proceed anyway. Decision logged 2026-08-23 (gstack-decision-log id `7c10facc-d522-49ab-b860-065b9811b118`).
3. EXIF/GPS stripping for personal photos has genuine, established privacy grounding (unlike AI-text-watermark removal) — and C2PA/EXIF/XMP deletion is the same *kind* of operation: deleting a discoverable metadata segment (JUMBF box, EXIF tag, XMP packet) wholesale, not forging or altering a signature, and does not require verifying or understanding the C2PA manifest's cryptographic contents. Deleting a self-contained JPEG marker segment or PNG chunk requires no checksum/length recalculation of the *retained* data (each is locally self-contained) — the one exception, relevant only if a RIFF-based format like WebP is ever added, is that RIFF's outer container carries a top-level chunk-size field that would need updating.
4. A client-side-only architecture (files never leave the browser) is a real mitigation for premise #2, not just an engineering preference — it makes "we cannot log your content" a structural fact rather than a policy promise. This is only true if *no* feature sends content to a server, which is why premise 5 exists.
5. **The Claude semantic-rewrite / statistical-watermark-disruption feature from the original scope is cut, not deferred.** Adversarial spec review flagged it as both unvalidated against Anthropic's own usage policy and a direct contradiction of the "never leaves the browser" trust claim. On top of that: a feature whose specific purpose is disrupting Claude's own compliance watermark is a targeted circumvention of a safety/transparency mechanism, a different category from deleting metadata fields on content the user owns. Not in scope for this product, full stop — not a "revisit if demand shows up" item.
6. **Anonymous, no registration gate, is the decided lead-capture model** (not left open) — consistent with premise 4's trust pitch; a registration gate would send a mixed signal against "we never see your content." Conversion happens via a persistent, non-blocking CTA into the consulting track, the same brand-halo role the Diagnostic plays, not a gated capture form.
7. **Regulatory-irony risk, distinct from the brand-adjacency risk in Premise 2.** The Problem Statement cites EU AI Act Article 50 / CA SB 942 / China GB 45438 as why this space is topical — but the tool's stated core use case (a compliance-conscious professional stripping provenance before sending a client deliverable, "worried about undisclosed-AI-use optics") is, read plainly, helping its own target audience avoid exactly the disclosure those laws compel. This is a sharper, more specific tension than the general plagiarism-evasion brand-adjacency: it's not just "looks bad," it's "the tool's pitch works against the transparency regime it cites as market context, for an audience recruited because they care about compliance." Considered and accepted as part of the same informed risk decision as Premise 2 (same log entry, `7c10facc-d522-49ab-b860-065b9811b118`) — not a separate unresolved item, but worth naming on its own line rather than folding silently into "brand risk."

## Approaches Considered

### Approach A: Server-side Next.js API route
Standard thin-route + `lib/` service pattern, reusing `sharp` (already a dependency) for image EXIF/XMP stripping. Effort S/M, Risk Medium — uploaded files touch the server, needs an explicit no-log/no-store policy, and Next.js's ~10MB body-size ceiling needs handling. Not chosen — weaker trust story than Approach C, and the whole point of premise 4 is to make "we never see your content" structurally true.

### Approach B: Python sidecar (deploy `guillaumemeyer/watermarks-remover` as-is)
Closest reference feature-parity via a second, private Render service. Effort L/XL, Risk High. **Rejected** — violates the documented single-Render-service architecture, adds a Python runtime nobody on the team maintains, and can't even reach full parity anyway: the reference repo's own README marks the SynthID scorer and CtrlRegen pixel-removal images "never published" (non-commercial research license, local-build-only).

### Approach C: Client-side / browser-only (recommended)
No server round-trip for any content — the one feature that would have required one (Claude rewrite) is cut per Premise 5. Text stripping is plain regex over the named code-point ranges (Target User & Narrowest Wedge), no dependency needed.

Image stripping is a **hand-rolled JPEG/PNG segment-and-chunk parser**, not a third-party library — this was the weakest link in the prior review round (no library was ever named or verified) and the fix is to not depend on one. Both formats have simple, fully documented container structures that a small parser can walk directly:
- **JPEG:** a flat sequence of marker segments (`0xFF` + type byte + 2-byte length + payload) up to the SOS marker, then raw entropy-coded data, then EOI. EXIF and XMP live in APP1 segments; C2PA's JUMBF manifest lives in APP11 segments (JPEG XT / C2PA embedding profile). Stripping means removing the matching APP1/APP11 segments and re-concatenating the rest — each segment is self-contained, so no other segment's length field needs recalculating (see Premise 3).
- **PNG:** a flat sequence of chunks (4-byte length + 4-byte type + data + 4-byte CRC). EXIF lives in the `eXIf` chunk (PNG spec since 2017); XMP lives in an `iTXt` chunk keyed `XML:com.adobe.xmp`; C2PA's JUMBF lives in a `caBX` chunk. Stripping means dropping the matching chunks; each chunk's CRC is local to itself, so no recalculation is needed for the chunks you keep.

**Orientation exception (found during `/plan-design-review` mockup generation):** JPEG's EXIF segment carries the orientation tag that determines whether the image displays right-side-up. Wholesale EXIF-segment deletion would strip orientation along with everything else — a portrait photo could display sideways after "cleaning." The parser must preserve the orientation tag specifically while removing everything else in the EXIF segment (GPS, camera model/serial, software, etc.). Same failure class the CEO review already flagged as a reason to avoid canvas re-encode — the fix belongs in the hand-rolled parser too, not just in ruling out canvas re-encode.

Effort M. Risk: **Low (architecture)** — no new runtime, no new dependency, no server data path — but **Medium (implementation), pending the parser spike** — the hand-rolled JPEG/PNG parser is the load-bearing, unverified bet the whole approach depends on (see Open Questions and The Assignment). Chosen because it delivers the v1 scope at the lowest infra cost, with the strongest trust story available (structurally true "we never see your content," not a policy promise) — which is also the most concrete mitigation for premise #2's brand-risk tension.

## Eng Review Findings (11-section /plan-ceo-review deep review, 2026-08-23)

90 findings surfaced across architecture, error handling, security, data flow, code quality, tests, performance, observability, deployment, trajectory, and design/UX. 14 were critical and each got an individual decision (all accepted as recommended); the remaining 76 are lower-severity engineering-quality notes, consolidated into Implementation Tasks below rather than negotiated individually. Full findings text: workflow transcript for run `wf_651bfd12-59a`.

**Critical decisions (all accepted):**
- `lib/image-metadata.ts` API is Uint8Array-in/Uint8Array-out only — never Buffer, never `server-only` (would break the one runtime v1 actually needs, unlike this repo's existing Buffer-based `lib/image-pipeline.ts`)
- Parser-verification spike must include a real multi-segment C2PA/JUMBF JPEG, not just single-segment fixtures — a parser that only strips the first segment reports false "cleaned"
- Both JPEG and PNG parsers need explicit bounds-checking on every length read (Uint8Array.slice() clamps silently instead of throwing) and a hard iteration cap — corrupted input must fail loudly, never hang the tab or silently corrupt output
- File-derived strings (EXIF/XMP values) render as React text/`.textContent` only, never `dangerouslySetInnerHTML`/`.innerHTML` — this repo's CSP keeps `unsafe-inline` and does not backstop XSS from rich-text rendering
- Removal log (renamed from "audit certificate") lists category/count only, never raw removed values — raw values would re-leak exactly what the tool exists to strip, via the one artifact the ICP is least likely to double-check
- Output must decode-check (`createImageBitmap`/`Image()`) before showing success — never hand back an undecodable "cleaned" file silently
- Parser spike converts to a permanent CI-gated Vitest suite with a checked-in fixture corpus, not a one-time manual check discarded after ship
- Add malformed-input tests (truncated files, overrun length fields, bad CRC, missing terminators) plus a seeded fuzz loop over the fixture corpus
- CTA click/outcome events wired into the existing `lib/analytics.ts` `track()` pattern; the plan's own "validate conversion before Phase 2" gate explicitly names its dependency on unshipped backlog item #41 (Plausible integration) rather than assuming real signal exists
- A distinct PARTIAL-removal UI/log state — some signals removed, one couldn't be safely stripped — never presented through the same "success" UI as a full clean
- Dropzone is a labeled, focusable `<input type="file">`-backed control (Tab-reachable, Enter/Space-activatable) — fixes both the WCAG keyboard-access gap and the mobile tap-to-select requirement with one control
- "Removal log" naming (see above)
- Visual identity inherits this site's existing design system, not sabrina.dev's template — only the functional "no setup, no signup" simplicity carries over
- Results screen: diff view is primary; explain panel expands per-signal on demand; removal-log download is one secondary action, not a 4th co-equal block — settle exact layout in `/plan-design-review`

## Open Questions

- **Verify the hand-rolled JPEG/PNG parser against real files before committing.** Test against a real C2PA-signed JPEG, a JPEG with EXIF+GPS data, and an XMP-tagged PNG. This is the load-bearing uncertainty in Approach C — if JUMBF/XMP placement turns out to be less regular in the wild than the spec suggests, the fallback is Approach A for images only (text stripping stays client-side regardless).
- **File-size ceiling.** No cap was set originally despite "works on mobile" being a stated success criterion; large images can crash a mobile tab doing client-side parsing. Needs a concrete number (tested against real devices) plus graceful-degradation UX for oversized files, before v1 ships.
- **PDF, OOXML (DOCX/XLSX/PPTX), and additional image formats (WebP/HEIC/SVG), deferred to phase 2.** Separate spikes needed before committing: (1) OOXML — hand-rolled rezip via a general-purpose zip library risks producing files Word/Excel/PowerPoint flags as needing repair; spike pass/fail criterion must include "round-trips through real Office and Google Docs without a repair prompt," not just "metadata is gone." Scope must also be enumerated precisely per format (docProps/core.xml, app.xml, custom.xml, embedded thumbnail) with tracked-changes/cached-author-list content editing explicitly out of scope (that's document editing, not metadata stripping — a different problem). (2) PDF — confirm C2PA-in-PDF and PDF Info-dict/XMP stripping both work correctly via `pdf-lib`. (3) WebP/HEIC/SVG each have different container mechanics from JPEG/PNG (WebP is RIFF-based with an outer size field to maintain; HEIC is a full ISOBMFF box structure; SVG is XML/script-bearing, not binary) and need their own scoping, not an assumption they're "the same as JPEG/PNG."
- **Marketing copy:** does the tool position explicitly against named detectors (Turnitin/GPTZero), the way most competitors do, or strictly as "AI content hygiene" (recommended, given the brand-risk finding)? Matters for SEO strategy given the premise that most users don't know the problem exists yet.
- Whether/how to add a "why this matters" education layer, given the status-quo premise that most visitors don't know the underlying problem exists — a content/SEO question, not just a tool-UX one.

## Success Criteria

A visitor can paste text or drop a JPEG/PNG, see exactly which detectable signals were found (the named invisible-Unicode code points in text; EXIF/XMP tags and C2PA/JUMBF presence in images — nothing else is claimed as detectable), strip them, and copy/download the result — entirely client-side, on mobile, within a stated file-size ceiling (TBD, see Open Questions). Client-side parsing of a single file at that size ceiling should be near-instant (sub-second) per CLAUDE.md's "every interaction must feel instant" standard — no arbitrary multi-second budget is assumed; if the file-size ceiling lands large enough to need one, state the number explicitly once that Open Question resolves. No server-side storage or logging of file content at any point, because no feature in v1 sends content to a server. A persistent, non-blocking CTA into the consulting track is present on every state of the tool (per Premise 6) — this is the actual lead-gen mechanism, not a registration form.
