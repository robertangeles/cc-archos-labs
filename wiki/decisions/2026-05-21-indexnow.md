Adds a push-indexing client so participating engines (Bing, Yandex,
Naver, Seznam.cz, Yep, Amazon) learn about publish / update / archive
events in minutes rather than waiting for the sitemap-driven crawl.
Google does NOT participate in IndexNow as of 2026-05; this is purely
the Bing-stack AIEO surface.

## Context

The sitemap fix shipped in [[2026-05-21-sitemap-aieo-fixes]] gives
crawlers a complete picture but discovery is still pull-based. For a
253-post corpus that's fine for backfill, but fresh content compounds
better with push. Bing accepted the sitemap and processed it same-day
(`Status: Success, URLs discovered: 314` per the Bing Webmaster
dashboard) — the push protocol they own (IndexNow) closes the discovery-
latency gap.

## D1 — Single endpoint, fire-and-forget

Two endpoint options exist: per-engine (`bing.com/indexnow`,
`yandex.com/indexnow`, etc.) or the global aggregator
(`api.indexnow.org/indexnow`). The global endpoint fans out to every
participating engine from a single submission. One POST per content
event.

Posture: never `await` the ping from a write path. A slow IndexNow
response (or the 429 case the FAQ flags) must not block an admin save.
Caller pattern:

```ts
void pingIndexNow([`${siteUrl}/blog/${slug}`]).catch(() => {});
```

`lib/indexnow.ts` already swallows exceptions internally; the outer
`.catch` is belt-and-braces against any future code path that might
re-throw.

## D2 — Same-URL 5-minute debounce, in-memory

The IndexNow FAQ specifically calls out: "wait at least 5 minutes
between resubmissions of the same URL" and recommends only re-pinging
on "meaningful content changes". A naive design would ping on every
admin save, which during active editing means 5-10 pings per post
within minutes.

Implemented as a module-scoped `Map<url, timestamp>` in `lib/indexnow.ts`.
Skipped if the most recent ping was < 5 minutes ago. State resets on
container restart — acceptable trade given Render's single-container
topology ([[deployment-architecture]]) and the small cost of one
duplicate ping after deploy.

The Map is bounded: cleanup sweeps entries > 1 hour old once the Map
exceeds 1000 entries. Won't grow unboundedly during long-lived process
runs.

## D3 — Key file: build-time generated at the canonical /{key}.txt URL

The spec offers two ways to host the verification key:

1. **Option 1 (Bing-prescribed)**: `/{api-key}.txt` literally at the
   domain root, with the filename being the key value.
2. **Option 2**: any publicly-accessible path, with `keyLocation`
   parameter in pings pointing at it.

**Initially shipped as Option 2** (route handler at
`app/indexnow.txt/route.ts` reading the key from env) because Next.js's
App Router doesn't support `[param].txt` folder names — there's no
clean dynamic-route way to serve a file whose URL contains the key
value.

**Switched to Option 1 same day** after reading Bing's getting-started
which leads with the `/{key}.txt` pattern as the example. Both shapes
are spec-compliant per the FAQ; Option 1 matches the example shown to
operators verifying the integration, which reduces "why doesn't ours
look like the docs" friction.

Implementation: `scripts/write-indexnow-keyfile.mjs` runs at `prebuild`
(wired in `package.json`), reads `INDEXNOW_KEY` from env, validates the
format (8–128 chars from `[a-zA-Z0-9-]`), and writes
`public/{INDEXNOW_KEY}.txt` containing the key as its body. Next's
static file server serves it at `https://archoslabs.xyz/{key}.txt` at
runtime.

`public/*.txt` is gitignored — the generated file only ever lives in
build artefacts. Key rotation = change the env var → next deploy
regenerates the file under the new name. No code change, no commit.

`pingIndexNow()` drops `keyLocation` from the payload — Option 1 means
engines auto-fetch the canonical URL.

## D4 — Triggers wired into existing write paths

| Trigger                              | File | Pings |
|--------------------------------------|------|-------|
| Post create (when public on save)    | `lib/posts-admin/index.ts` `createPost` | `/blog/<slug>` |
| Post update (any save while public)  | `updatePost` | `/blog/<slug>` + old `/blog/<previousSlug>` if renamed |
| Post archive                         | `archivePost` | `/blog/<slug>` (signals 404; engines drop) |
| Post restore from archive            | `restoreFromArchive` | `/blog/<slug>` if it's back to public |
| Scheduled publisher cron flip        | `lib/posts-admin/scheduled-publisher.ts` | Batch list of all newly-public slugs |
| CMS page create (when published)     | `lib/pages/index.ts` `createPage` | `/<slug>` |
| CMS page update (any save while pub) | `updatePage` | `/<slug>` + old `/<previousSlug>` if renamed |
| CMS page archive                     | `archivePage` | `/<slug>` |
| CMS page restore                     | `restoreFromArchive` | `/<slug>` if back to public |

The "is this public" predicate lives in each service module (post:
`status='published' AND visibility='listed' AND archivedAt IS NULL`;
page: `status='published' AND archivedAt IS NULL`). The URL shape is
also domain knowledge per surface. The `pingIndexNow()` core stays
generic — it doesn't know what URLs mean.

The slug-rename case from [[2026-05-21-sitemap-aieo-fixes]] (the
`ai-workforce-strategy-without-people-plansai-workforce-strategy-without-people-plans`
data corruption) had no in-codebase signal mechanism to tell engines
the old URL was gone. With this PR, any future slug edit through the
admin will ping both old and new URLs automatically.

## D5 — Dev environment is silent

`pingIndexNow()` returns `{ status: 'skipped', reason: 'non-production' }`
when `NODE_ENV !== 'production'`. Local edits during development don't
generate noise against Bing's quota or pollute the engines' view of
the site state. The dev `.env.local` need not (and should not) set
`INDEXNOW_KEY`.

## What didn't change

- The sitemap. IndexNow complements it; engines that don't participate
  (Google) still rely on it. The PR doesn't touch `app/sitemap.ts` or
  any of its inputs.
- Admin UX. The ping is fire-and-forget after the DB commit. The save
  UX has no new latency, no new error states, no new visible feedback.
  Operators may inspect server logs for `[indexnow]` lines if they want
  to verify behavior.
- The retry posture. A 429 or 422 from IndexNow gets logged once and
  marked debounced — the same URL won't re-ping for 5 minutes. No
  exponential backoff, no DB-backed queue. If a class of pings fails
  consistently it'll appear in the logs and we'll know.

## Verification

- `pnpm tsc --noEmit` clean.
- `pnpm test` 538/538 pass — 11 new `lib/indexnow.test.ts` cases cover
  env-var short-circuits, dev-skip, payload shape, deduplication,

  throw handling.
- `pnpm lint` clean (one pre-existing warning in `tmp/walkthrough.mjs`

- Local `curl /indexnow.txt` with `INDEXNOW_KEY` unset returns HTTP 503

- After merge + Render env-var set, the same curl will return HTTP 200
  + the key as plain text.

## Rollout

1. Merge the PR.
2. Generate a key: `node -e "console.log(require('crypto').randomBytes(16).toString('hex'))"`
3. Add `INDEXNOW_KEY=<value>` to Render → service → Environment. Redeploy.
4. Verify `curl -s https://archoslabs.xyz/indexnow.txt` returns the key.
5. Edit any post in `/admin/blog/posts/<id>` and save while published.
   Check Render logs for `[indexnow]` lines — expect either silence
   (success, 200/202) or a single error line per attempt.
6. Bing Webmaster → Configure My Site → IndexNow shows the key being
   used. Within ~1 hour of save, the edited URL should show fresh
   crawl activity in the Bing dashboard.

## Future work (out of scope)
